# deep 모드 — 후보별 통제 비교

사용자가 deep 비교를 요청했을 때 수행한다. 정적 충돌만으로 해결할 수 있는 문제에 전체 A/B를 강제하지 않는다. 목적은 특정 후보 지침이 현재 작업에 기여하는지 확인하는 것이다.

1. 최근 관련 실사용에서 대표 요청과 과거 실패·경계 사례를 고른다. 비교 전에 성공 조건, 지켜야 할 계약, 확인할 행동과 비용 범위를 정한다. 고정된 전체 표본 수를 채우기 위해 무관한 작업을 추가하지 않는다.
2. **같은 모델·reasoning·호스트 버전·도구·작업 입력·필수 사용자/프로젝트 계약을 유지하고 후보 지침만 바꾼다.** 격리된 복사본 또는 재현 가능한 새 세션을 사용한다. 모델 교체 효과와 지침 변경 효과를 동시에 바꿔 귀속하지 않는다.
3. 현행과 후보의 읽힌 지침 버전, 결과, 계약 통과, 질문·중단·위임·불필요한 검증을 관찰한다. 이전 실행을 기준선으로 재사용하려면 비교 조건이 맞아야 하며 차이를 숨기지 않는다. 실행 명령과 지원 기능은 현재 호스트에서 확인하고, 한 호스트의 결과를 다른 호스트의 증거로 쓰지 않는다.
4. 관련 판정이 애매하거나 실패했을 때만 그 사례를 추가 확인한다. 동등한 결과는 **해당 표본에서 차이를 확인하지 못함**이다. 전체 무용성이나 드문 실패 방지 효과의 부재를 증명하지 않는다. 삭제 후보 승격에는 계약·의존성 보존과 충분한 관련 근거가 필요하다.
5. 정적 판단, 관찰 결과, 원인 귀속의 한계, 수정/보존/미검증 결정을 Phase 3에 합친다. 비용·시간·품질 개선은 실제 비교 측정이 있을 때만 보고한다.

전체 셋업 비활성화는 기본 방법이 아니다. 공급자 간 상호작용을 분리할 필요가 입증되고 사용자가 그 시험을 요청한 경우에만 별도 격리 환경에서 검토한다. 필수 정책은 유지하며, 여러 요소를 함께 바꾼 결과로 개별 스킬의 삭제를 확정하지 않는다.
